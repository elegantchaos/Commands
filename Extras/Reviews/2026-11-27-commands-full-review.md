## Summary

**Needs rework before release.** Commands provides a reusable execution boundary for application actions and presents them through SwiftUI and UIKit. The product split fits its consumers, but execution can bypass the running-state check, confirmation can be skipped or applied to the wrong request, both undo implementations retain their owners, and async history can corrupt its undo/redo boundary.

Guidance read includes `baseline:git`, `baseline:records`, `baseline:refresh`, `baseline:review`, `baseline:standards`, `baseline:summaries`, `baseline:tools`, `swift:concurrency`, `swift:language`, `swift:swiftdata`, `swift:swiftui`, `swift:swiftui-trace`, `swift:testing`, and `swift:validation`.

## Findings

### Blocking

1. **A hosted alert can execute a different action from the one shown.** The host reads the title and labels from the presented request, but its buttons accept or cancel the presenter's *current* request. Submitting a second request replaces the first while the Boolean stays true. SwiftUI documents that it ignores changes to the presentation data once the alert appears, so accepting an alert for A can execute B. The existing presenter test actually requires replacement, without presenting an alert. Bind actions and dismissal to the displayed request ID and refuse or queue new requests until the displayed one closes. Test A displayed, B requested, then A accepted or cancelled. [CommandsHost.swift:48](../../Sources/CommandsUI/CommandsHost.swift#L48) · [CommandPresenter.swift:35](../../Sources/CommandsUI/CommandPresenter.swift#L35) · [CommandPresenterTests.swift:53](../../Tests/CommandsUITests/CommandPresenterTests.swift#L53) · [Apple’s alert contract](https://developer.apple.com/documentation/swiftui/view/alert%28_%3Aispresented%3Apresenting%3Aactions%3Amessage%3A%29?changes=_8)
2. **UIKit menus and file importers skip declared confirmation.** The UIKit invocation goes straight to `performWithoutWaiting`. The file importer does the same on completion, including the contextual-menu variant that uses the shared modifier. A command that asks for confirmation when surfaced through a SwiftUI button therefore executes immediately in these adapters. This breaks the project rule that invocation paths share safety rules. Route UI activation through a confirmation-aware entry point, let import commands confirm the selected input before execution, and make any programmatic preapproval or bypass explicit. Exercise a confirming command through each adapter. Undo and redo need an explicit policy too, since History and Foundation undo both invoke commands without UI confirmation and Foundation's callback is synchronous. [CommandCentreDelegate.swift:43](../../Sources/CommandsUI/CommandCentreDelegate.swift#L43) · [ImporterCommandModifier.swift:46](../../Sources/CommandsUI/Modifiers/ImporterCommandModifier.swift#L46) · [CommandButton.swift:63](../../Sources/CommandsUI/Views/CommandButton.swift#L63) · [HistoryEntry.swift:42](../../Sources/Commands/HistoryEntry.swift#L42) · [CommandCentreWithUndo.swift:73](../../Sources/Commands/CommandCentreWithUndo.swift#L73) · [AGENTS.md](../../AGENTS.md)
3. **A command reported as running can start again.** The centre consults `isRunning` for presentation but omits it from the guard in `perform`. A probe marked an enabled command as running, verified that the centre returned `.running`, then watched execution return successfully and mutate the centre. This affects direct and fire-and-forget execution, including History entries and UI actions arriving before a redraw. Foundation undo already checks the centre's resolved availability, while the public `performAndRegisterUndo` helper also lets callers bypass gates and lifecycle hooks altogether. Give both paths a common admission check that honours the supplied history context, and narrow or explicitly name the unchecked synchronous primitive. [CommandCentre.swift:41](../../Sources/Commands/CommandCentre.swift#L41) · [CommandCentre.swift:66](../../Sources/Commands/CommandCentre.swift#L66) · [CommandCentreWithUndo.swift:47](../../Sources/Commands/CommandCentreWithUndo.swift#L47)
4. **The Foundation undo closure keeps the manager and centre alive.** The manager retains its registered handler, which ignores the supplied target and captures both the manager and the centre. The example command pair also stores the same manager, so weakening the closure's explicit manager capture alone leaves a cycle through the commands. A probe registered one undo, dropped both external owners, and found both weak references still populated. Keep the manager outside the retained command payload or give it weak storage by construction, use the handler's target to recover the centre where possible, and make both lifetimes regression tests. [CommandCentreWithUndo.swift:73](../../Sources/Commands/CommandCentreWithUndo.swift#L73) · [CommandWithUndo.swift:19](../../Sources/Commands/CommandWithUndo.swift#L19) · [IncrementCountCommand.swift:23](../../Extras/Example/Example/Example/IncrementCountCommand.swift#L23) · [Apple’s undo registration contract](https://developer.apple.com/documentation/foundation/undomanager/registerundo%28withtarget%3Ahandler%3A%29?changes=_8)
5. **A history entry retains the centre that owns it.** The documented setup is centre → history service → entry. The entry has a strong `centre` property and its execution and availability closures also capture the centre strongly. A probe ran one reversible command, dropped the owning centre, and found it still alive. The example's History tab uses this ownership shape directly. Keep the owner out of its history's strong reference graph and define how a detached entry behaves when its centre has gone away. Test teardown with both undo and redo entries. [HistoryEntry.swift:26](../../Sources/Commands/HistoryEntry.swift#L26) · [HistoryEntry.swift:38](../../Sources/Commands/HistoryEntry.swift#L38) · [HistoryExampleCentre.swift:15](https://github.com/elegantchaos/Commands/blob/5b9d294030d28e52a21a74d0216bcf1b0e525443/Extras/Example/Example/Example/HistoryExampleCentre.swift#L15)
6. **Recording history during an async reversal corrupts the cursor.** Public `recordUndo` mutates both the stack and cursor while `performUndo` or `performRedo` holds a saved index across an `await`. In the probe, recording a new step during a suspended undo put that new step on the redo side even though it had never run. A registration during redo can truncate the very entry the suspended operation will later replace or remove. Enforce the mutation invariant inside the service for direct registrations as well as normal forward commands, and add matching tests for both directions. ### Should Fix

7. **UIKit menu dispatch can run another menu item's command.** The registry is keyed by the descriptive command ID. Building a second menu item with an instance of the same command type and a different argument or centre overwrites the first item's invocation. Both items then resolve to the second instance. Stack's per-tag delete command, which carries a tag alongside a fixed command ID, illustrates why stable command IDs and menu invocation identity need different lifetimes. Give each simultaneously live item an invocation identity scoped to its menu or attach an action directly where UIKit permits it. Cover two instances with the same descriptive ID and test eviction when menus are rebuilt. This is source-confirmed and was not reproduced through UIKit's responder chain. [CommandCentreDelegate.swift:21](../../Sources/CommandsUI/CommandCentreDelegate.swift#L21) · [CommandCentreDelegate.swift:43](../../Sources/CommandsUI/CommandCentreDelegate.swift#L43) · [CommandCentreDelegate.swift:80](../../Sources/CommandsUI/CommandCentreDelegate.swift#L80)
8. **The History buttons can offer a step the service will refuse.** The buttons check entry availability and the current undo or redo mode, while the service also rejects operations during any tracked forward command. The centre's availability query for the reversal does not include the forward count. This leaves a visible enabled button whose action can only log `forwardCommandInProgress`. The docs say history waits, but the service throws immediately. Expose a history-level availability query for each direction and use it for both buttons, including the service's operation gate. Clarify that requests made while forward work is active are rejected. [HistoryUndoButton.swift:37](../../Sources/CommandsUI/Views/HistoryUndoButton.swift#L37) · [HistoryRedoButton.swift:37](../../Sources/CommandsUI/Views/HistoryRedoButton.swift#L37) · [HistoryService.swift:156](../../Sources/Commands/HistoryService.swift#L156) · [Commands README](../../Sources/Commands/README.md#history)
9. **The ordinary importer keeps the first command it was given.** The button puts its incoming command in writable `@State`. With stable SwiftUI identity, a parent that swaps the command's target or options keeps the previous command, and the picker writes its result into that old instance. Keep current command input separate from picker state. Snapshot the command when opening, and dispatch an invocation carrying that picker's result. Exercise a parent update before opening and after opening. The contextual-menu API also has independent command inputs in the show button and modifier, which can disagree. On watchOS, the enabled importer buttons change a binding with no picker attached. Advertise platform support at the control boundary. ## Place in the Project

**Keep the Commands and CommandsUI products together with their current dependency direction. Add a migration note for the breaking release.** The package's core action and centre protocols fit the programmatic App Intents in Stack and the narrow TipJar provider protocols in ActionStatus. The separate UI product fits Bookish's environment injection and ActionStatus's file-picker controls. The meaningful overlaps are at the adapter boundaries listed above, so splitting the package further or moving UI policy into each app would spread the execution rules across more code. The reachable Bookish checkout still uses `CommandsHost(commander:)`, and ActionStatus's picker commands use `ImporterCommandURLState`. Record the host rename, history migration, lifecycle-hook signatures, and Swift toolchain floor together so upgrades can be checked systematically. These checkouts were used as consumer evidence and were not built against the reviewed package.

## Codebase Effect

### Made Obsolete

**Remove the deprecated `confirmableButton` and `confirmableToolbarItem` forwarding aliases in the breaking release after checking consumer migration.** They now behave exactly like the ordinary controls. Their names encourage callers to think control choice confers confirmation. The October journal records that some consumers used those names for precisely that purpose. [CommandCentre+UI.swift:75](../../Sources/CommandsUI/CommandCentre+UI.swift#L75) · [Commands Host journal](../Journal/2026-10-01-commands-host.md)

### Simplification Now Possible

**Make the history service own balanced forward tracking when a centre also observes command lifecycle.** Tracking and app hooks currently share the same overridable protocol witnesses. A conformer that customises just one hook can omit the decrement and block history indefinitely, or omit the increment and trip the service precondition. Separate mandatory bookkeeping from the app's notification hooks at the execution boundary. This also narrows the public begin/finish API and removes an obligation from consumer code. [CommandCentreWithHistory.swift:29](../../Sources/Commands/CommandCentreWithHistory.swift#L29) · [HistoryService.swift:136](../../Sources/Commands/HistoryService.swift#L136)

### Duplication

**Share the History control implementation once it has a service-level availability contract.** Undo and Redo have parallel state lookup, rendering and task/error plumbing. A private direction-driven control can serve both public entry points, carry direction-specific localized labels, and keep disabled or failed behavior aligned. Foundation integration still needs its own synchronous execution and system ownership contract. [HistoryUndoButton.swift:36](../../Sources/CommandsUI/Views/HistoryUndoButton.swift#L36) · [HistoryRedoButton.swift:36](../../Sources/CommandsUI/Views/HistoryRedoButton.swift#L36)

### Design Clarity

**Define what a history entry promises about the state around it.** The service records forwards in completion order, drops a performed entry whose inverse is nil, and retains the other entries across that hole. A successful new forward that supplies no reversal also leaves any existing redo branch intact. These rules work for independent counter-like changes and can be wrong for commands that capture snapshots or depend on earlier effects. Specify the conditions under which overlap, traversing past an irreversible entry, and preserving redo are valid. Add tests with dependent state changes before choosing whether to serialize, invalidate history, or represent a barrier. [CommandCentreWithHistory.swift:42](../../Sources/Commands/CommandCentreWithHistory.swift#L42) · [HistoryService.swift:119](../../Sources/Commands/HistoryService.swift#L119) · [HistoryService.swift:214](../../Sources/Commands/HistoryService.swift#L214)
